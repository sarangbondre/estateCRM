# CR-014: Gateway timeouts that survive Vercel cold starts

| | |
|---|---|
| Raised | 2026-10-02, during the pilot smoke test on Vercel (https://estatecrm-nu.vercel.app) |
| Affects | web gateway (`services/web/src/application/gateway.ts`, `src/config.ts`), provisioning runbook. Contracts unchanged |
| Status | APPROVED 2026-10-02, auto-approved (technical, questionnaire B3); listed for the product owner's review |

## What happened
On a cold backend function the web gateway answers 503 although the call succeeds. Seen twice on 2026-10-02:
- `POST /v1/chat/conversations` (correlation `01a0fd89-0701-73ad-8089-036e7dd50a14`): web started at 16:53:27.8 UTC. The
  first insight invocation began 4.2 s later and took 906 ms. The gateway's retry began at 16:53:34.1 and took 500 ms.
  Both exceeded the 2 s first-byte timeout, so web returned 503 after 5.1 s. The conversation was created anyway; the
  Idempotency-Key replay made the second attempt harmless.
- `GET /v1/notifications` → 503 right after sign-in (journeys cold).

The 2 s timeout is the CLAUDE.md §3.5 default, written into the contracts as `x-timeout-ms: 2000`. On Vercel a function
that has scaled to zero needs about 3–5 s to start (bundle load plus first database connection), so the first call after
idle always fails. The scheduler calls every service each minute, which keeps them warm most of the time but not always
(a new instance for concurrent traffic also starts cold).

## Decision (implemented)
The option closest to the approved documents: the contracts keep `x-timeout-ms: 2000` as each operation's processing
budget, and the **web gateway adds a cold-start allowance** to its wait for the downstream service:
- `COLD_START_ALLOWANCE_MS` (web env; `WEB_COLD_START_ALLOWANCE_MS` also works): **6000 ms by default on Vercel**
  (`VERCEL` is set), **0 locally**. The first-byte and total timeouts become 2 s + allowance; the one retry for
  idempotent calls is unchanged.
- Warm calls are unaffected. p95 stays well under 300 ms, and the allowance only matters while a function is starting.
- Service-to-service calls keep 2 s with retry; they run in the background (queues, drains) and retry anyway.
- Test: `services/web/tests/gateway.test.ts`. A service whose first byte arrives after 2.5 s answers 200 with the
  allowance, and the same test fails without it.

## Alternatives considered
- Keep 2 s and accept 503s after idle: staff see "not reachable" on the first click of the day.
- A keep-warm ping: already in place through the scheduler. It isn't enough on its own.
- Vercel Pro with always-on instances: costs money and is out of scope for the pilot (CR-005).

## Impact on later stages
None on contracts, schemas, events or service boundaries. The capacity plan's latency targets are unchanged; cold
start (3–5 s on Vercel Hobby) is a known pilot limitation, mitigated by the scheduler calling every service each minute.
