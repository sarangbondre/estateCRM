# CR-001: Website may show building/society name and landmark

## What
Change BRD assumption **A-11** and the related wording in §4 Module C, metric M8 and risk R8.

**Currently (BRD v0.3):**
> A-11: "Not exact address" means the API shows the locality/area (for example "Andheri West") but not the
> building or society name, wing, flat number or street address.

**Proposed:**
> A-11: The Listings API may show **locality**, **building/society name** and **nearby landmark**
> (for example "Lodha Fiorenza, Goregaon East, near Oberoi Mall"). "Exact address" means **wing/tower,
> flat/unit/shop number, plot/survey number and full street address**. These are never exposed.
> Contact details (names, phone numbers, emails) are never exposed.

Consequential edits:
- §4 Module C, "Never exposed": replace "(building/flat number, street-level location)" with
  "(wing/tower, flat/unit/shop number, plot/survey number, full street address)". Add building/society
  name and landmark to "Exposed".
- M8: unchanged in intent. "Exact address" now uses the new definition above.
- R8: the leak to guard against is unit numbers and contacts, not building names.
- OQ-17: closed.

## Why
Product-owner decision in Stage 2 (answer to OQ-17): buyers on the 11estate websites need the building and
a landmark to judge a property. Only unit-level detail and contact details are sensitive.

## Impact on later stages
- **Stage 2 (PRD):** Listings API field list and the publishing-approval screen include building/society
  and landmark. The publishing check scans for unit numbers and contacts. Already reflected in the PRD draft.
- **Stage 3–4:** the listing data model must store unit-level address fields separately from building and
  locality, so they can be withheld reliably. There are no approved later-stage documents to reopen.
- **Risk:** combining building name with floor and configuration can sometimes identify a single flat.
  Publishing requires manual approval (PRD decision), which mitigates this.
