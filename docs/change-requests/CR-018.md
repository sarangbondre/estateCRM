# CR-018: Move compute from Vercel to AWS (option A: servers only; Supabase stays)

| | |
|---|---|
| Raised | 2026-10-04 by the product owner ("lets go with option A") |
| Affects | ADR-0002 and HLD §10 / §10.1 (hosting), `docs/04-lld/data-hosting.md` (network row), `docs/04-lld/capacity-plan.md` (compute rows), implementation rules D-4 (Dockerfile), provisioning and deploy runbooks, `infra/`, `.github/workflows/` |
| Status | **APPROVED 2026-10-04** (`APPROVED: CR-018`) |

## What
Run the seven apps (web + six services) as containers on **AWS ECS Fargate in `ap-south-1` (Mumbai)** instead of
Vercel. Everything stateful stays on **Supabase Mumbai**: Postgres (per-service schema and role), Auth (Google
sign-in), Storage, pgmq queues and the pg_cron scheduler. This is step A of the AWS path in ADR-0002. Step B (RDS, S3,
SQS/SNS, EventBridge) is a later CR.

| Item | Today (Vercel) | After CR-018 |
|---|---|---|
| Compute | Vercel Functions, one project with Services (CR-013) | ECS Fargate service per app, **min 2 tasks**, autoscaling on CPU (max 4). Linux/ARM64 (Graviton) |
| Images | Built by Vercel from source | `services/<svc>/Dockerfile` (multi-stage, Node 24, `pnpm deploy`), pushed to **ECR** by GitHub Actions (OIDC role, no stored keys) |
| Entry | `vercel.json` routes and rewrites | **Application Load Balancer** + ACM certificate on the product domain. Path rules: `/svc/<svc>/*` → that service, `/public/*` → listings, everything else → web. Services already accept the prefixes (#92, #93) |
| Service to service | Vercel bindings | **ECS Service Connect** (private DNS such as `http://records:3002`) inside the VPC; `SVC_<S>_URL`, `RECORDS_URL`, `INTAKE_URL`, `WEB_URL` set explicitly |
| Network | Public internet + TLS | VPC: public subnets (ALB, NAT gateway), private subnets (tasks). Tasks reach Supabase, Google and Hugging Face through the NAT; one fixed egress IP |
| Secrets | Vercel environment variables | **AWS Secrets Manager**, one JSON secret per app, injected into the task at start; IAM limits each task to its own secret |
| Logs and metrics | Vercel logs (may be stored outside India) | **CloudWatch Logs and alarms in Mumbai**; OpenTelemetry unchanged |
| Scheduler | pg_cron + pg_net → `https://<vercel domain>/svc/<svc>/…` | Same jobs, base URLs re-pointed to `https://<domain>/svc/<svc>` with the `configure-scheduler` workflow |
| Deploy | Vercel Git integration | Per-service GitHub workflow: test → build image → push → `aws ecs update-service` (rolling, health-checked), so each service still deploys alone |
| IaC | Terraform (Vercel and Supabase providers) | `infra/aws/` Terraform: VPC, ECR, ECS cluster and services, ALB, ACM, Secrets Manager, CloudWatch, IAM, GitHub OIDC role. State in an S3 bucket with locking |

Sizing at launch (capacity plan to be re-confirmed by the load test): six backend services at 0.25 vCPU / 0.5 GB × 2
tasks each, web at 0.5 vCPU / 1 GB × 2. DB pool caps unchanged (`POOL_MAX` 3 per task → at most 14 tasks × 3 = 42
connections through Supavisor).

## Why
- Vercel Hobby is **non-commercial only** (CR-005). The product needs a commercially usable host.
- **Cold starts go away.** Containers stay running, so the gateway's cold-start allowance (CR-014) becomes 0 because `VERCEL` isn't set.
- It closes CLAUDE.md deviations: §3.6 **minimum 2 instances**, §3.8 **secrets in a secrets manager**, and part of
  §3.8 **private network** (services are private; Supabase stays reached over TLS until step B).
- Logs stay in India.

## Impact
- **No contract, schema or event change.** Services move one at a time behind the same domain.
- **Code:**
  - a Dockerfile per app;
  - web runs as a standalone Next.js server;
  - config reads explicit service URLs (already supported for local development);
  - the Vercel-only parts (`vercel.json`, `index.ts` entries) stay until cutover, then are removed.
- **Supabase:** move the project to **Pro** before commercial use (Free pauses idle projects). The Supabase project and data
  aren't touched.
- **Cost (estimate, to confirm with the AWS pricing calculator):** about US$200–250/month.
  - Fargate ≈ $150
  - NAT gateway ≈ $35 + data
  - ALB ≈ $20
  - CloudWatch ≈ $10
  - Secrets ≈ $3
  - Supabase Pro ($25+) on top.
- **Later stages:** Stage 5 gets a task group "AWS-A" (below). Stage 7 continues with it. The final load test is re-run on the
  Fargate sizes.

## Tasks (AWS-A)
| ID | Task | Size |
|---|---|---|
| AWS-A1 | Dockerfiles for the 7 apps (multi-stage, non-root, health check) + local `docker compose` smoke test | M |
| AWS-A2 | `infra/aws` Terraform: VPC, NAT, ECR, ECS cluster, Service Connect, ALB + path rules, ACM, CloudWatch, Secrets Manager, IAM, GitHub OIDC role, S3 state | L |
| AWS-A3 | GitHub workflows: build + push + deploy per service; a manual `aws-bootstrap` workflow for Terraform | M |
| AWS-A4 | Config: explicit service URLs; web standalone build; secrets layout per app | S |
| AWS-A5 | Deploy to a staging hostname, run the smoke and contract tests, then load test to the NFRs | M |
| AWS-A6 | Cutover: DNS to the ALB, Google OAuth and Supabase redirect URLs, scheduler re-pointed, Vercel kept one week as fallback, then removed | S |

Estimate: **1–1.5 weeks** of build, plus the product owner's AWS account setup, domain and approval.
